# Rahma Mobile Build Plan

**Date:** 2026-05-14
**Status:** PLAN. No mobile source has been committed yet.

## Framework decision

The recommendation is **Flutter** (single Dart codebase, strong
Arabic-RTL primitives via `flutter_localizations` and `bidirectional`
text widgets, native performance on both platforms, simple Android +
iOS pipelines).

Acceptable alternatives the operator may choose instead:

| Option | Pros | Cons |
|---|---|---|
| **Flutter (recommended)** | one codebase; first-class RTL; mature Material+Cupertino | Dart team size |
| React Native (Expo) | JS team can contribute | RTL bidi edge cases; native module pain |
| Native (Kotlin + Swift) | best per-platform UX | two codebases; double the cost |

The mobile source, when chosen, lives under `apps/mobile/` with:

- `apps/mobile/android/` (auto-generated by Flutter create)
- `apps/mobile/ios/` (auto-generated by Flutter create)
- `apps/mobile/lib/` (Dart source)
- `apps/mobile/pubspec.yaml`
- `apps/mobile/test/`

## Project bootstrap (Flutter path — operator-run)

```bash
cd apps
flutter create --org com.rahma --project-name rahma_mobile mobile
cd mobile
```

Once the source is present, the placeholder workflows turn into real
builds — see `RAHMA_ANDROID_IOS_RELEASE_PLAN.md`.

## Build pipeline (planned, path-guarded)

`.github/workflows/rahma-mobile-ci.yml` runs only when `apps/mobile/**`
exists. It executes the chosen framework's pipeline:

- Flutter: `flutter pub get`, `flutter analyze`, `flutter test`, `flutter build apk --release`, `flutter build ipa --release` (iOS only on macOS runner).
- React Native: `npm ci`, `npm run lint`, `npm test`, `cd android && ./gradlew assembleRelease`, `cd ios && xcodebuild ...`.

The workflow is not generated this sprint because:

- Picking the wrong framework today would force a rewrite.
- A path-guarded workflow without source compiles to "no-op" anyway.

When the operator commits the first mobile project file, this sprint's
follow-up adds the workflow at the same time.

## Communication contract

The mobile app talks only to `https://api.<final-rahma-domain>` (placeholder
`api.rahma.example`). No other origins, no telemetry destinations, no
third-party SDKs except those the operator approves explicitly.
